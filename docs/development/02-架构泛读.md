# Rich 架构泛读（模块划分与模块间接口）

> 承接 `01-代码度量分析.md`，本文档给出 Rich 的总体架构、主要模块职责与模块之间的接口。
> 结论均以源码为依据，接口签名取自 v14.3.4 的实际代码。

## 1. 一句话架构

Rich 把“要显示什么”和“怎么显示到终端”彻底分开：**组件描述内容，Console 负责绘制，
两者之间用 Segment 这一中间表示通信**。

## 2. 四层流水线

```
第 1 层  可渲染对象层 (Renderable)
         Text / Table / Panel / Tree / Markdown / Syntax / Progress / Layout ...
         职责：描述“显示什么”。不查询终端，不做平台判断。
            │  __rich_console__(console, options) -> Iterable[Segment]
            │  可选 __rich_measure__(console, options) -> Measurement
            ▼
第 2 层  几何与协议层 (Geometry / Protocol)
         ConsoleOptions / Measurement / Constrain / Align / Layout
         职责：把可用宽高作为不可变上下文向下传递；测量尺寸；决定换行或裁剪。
            │  产出 Iterable[Segment]
            ▼
第 3 层  中间表示层 (Segment IR)
         Segment(text, style, control) / Style / Color / ControlCode
         职责：用统一三元组表达一切可见内容；所有几何操作都定义在 Segment 上。
            │  按终端能力转成 ANSI 转义序列
            ▼
第 4 层  输出层 (Output)
         Console._render_buffer / _win32_console / TextIO / theme / cells
         职责：真正写出字符；Windows 走 WriteConsoleW，其它平台写 ANSI 序列。
```

## 4. 模块之间的接口

### 4.1 渲染协议（第 1 层 ↔ 第 2 层）

```python
def __rich_console__(self, console: Console, options: ConsoleOptions) -> RenderResult: ...
def __rich_measure__(self, console: Console, options: ConsoleOptions) -> Measurement: ...
```

- **协议而非继承**：任何对象实现 `__rich_console__` 即可被渲染，第三方扩展无需继承基类。
- **两个协议分离的原因**：表格必须先量出各列宽度才能决定何时换行，而渲染又依赖已决定的
  宽度，这构成循环依赖；把“量”与“画”拆成两个方法正好打破该循环。
- **惰性且可嵌套**：返回的可迭代对象里若仍是可渲染对象，`Console.render_lines` 会继续展开，
  直到全部变成 `Segment`；`rich.protocol.rich_cast` 负责类型适配。

### 4.2 中间表示 Segment（第 2 层 ↔ 第 3 层）

```python
class Segment(NamedTuple):
    text: str
    style: Optional[Style] = None
    control: Optional[Sequence[ControlCode]] = None

    # 几何代数（全部以“单元格”为单位）
    cell_length: int
    def is_control(self) -> bool: ...
    def split_cells(self, cut: int) -> Tuple["Segment", "Segment"]: ...
    @classmethod
    def split_and_crop_lines(cls, segments, length, style=None, pad=True, ...): ...
    @classmethod
    def adjust_line_length(cls, line, length, style=None, pad=True): ...
    @classmethod
    def align_top(cls, lines, width, height, style=None, new_lines=False): ...
    @classmethod
    def align_middle(cls, lines, width, height, style=None, new_lines=False): ...
    @classmethod
    def align_bottom(cls, lines, width, height, style=None, new_lines=False): ...
    @classmethod
    def simplify(cls, segments): ...
    @classmethod
    def divide(cls, segments, cuts): ...
```

“让 N 个组件 × M 种输出格式的实现量从 N×M 降到 N+M”是这个接口最大的价值。

### 4.3 几何上下文 ConsoleOptions（第 2 层内部）

```python
class ConsoleOptions:
    size: ConsoleDimensions        # (width, height)
    legacy_windows: bool           # 是否 Windows 传统控制台
    min_width: int
    max_width: int
    justify: Optional[JustifyMethod]
    overflow: Optional[OverflowMethod]
    no_wrap: Optional[bool]
    height: Optional[int]
    is_terminal: bool
    encoding: str

    def update(self, **kwargs) -> "ConsoleOptions": ...    # 返回新对象
    def update_width(self, width: int) -> "ConsoleOptions": ...
    def ascii_only(self) -> bool: ...
```

**关键约定**：`update*` 一律返回新对象，因此每一层都能安全地收窄宽度而不影响兄弟节点。

### 4.4 样式解析（Theme ↔ Style ↔ Color）

| 接口 | 形式 | 语义 |
| --- | --- | --- |
| `Theme(styles, inherit=True)` | 构造 | 命名样式表 |
| `Console.get_style(name, *, default=None)` | 查表 | 语义名 → Style；主题栈顶优先，最后回退到解析字面样式 |
| `Style.parse("[bold red on blue]")` | 解析 | 样式字符串 → 不可变、可哈希的 Style |
| `Style.combine(styles)` / `Style.chain(*styles)` | 合并 | 后者非默认属性覆盖前者 |
| `Style.render(text, *, color_system, legacy_windows)` | 渲染 | Style → ANSI 转义序列（含能力降级） |
| `Color.parse("rgb(255,0,0)")` | 解析 | 四种颜色写法 → Color |
| `Color.get_truecolor(theme, foreground)` | 折算 | 任意颜色 → 真彩色三元组 |
| `Color.downgrade(system)` | 降级 | 按终端能力折算颜色 |

### 4.5 宽度度量（cells）——全局唯一的度量约定

```python
def cell_len(text: str) -> int: ...          # 缓存版为 cached_cell_len
def set_cell_size(text: str, total: int) -> str: ...   # 裁剪/补齐到 total 格
def chop_cells(text, width) -> List[str]: ...          # 按格切行，不切开宽字符
def get_character_cell_size(character: str) -> int: ...  # 单字符宽度（lru_cache）
```

`Text.cell_len`、`Segment.cell_length`、`Table` 列宽、`Panel` 边框、`Progress` 填充
最终都调用它。**任何新增排版能力都必须复用它**，否则会与既有组件对“一列多少格”的
理解产生分歧。

## 5. 一份依赖度数数据（用于确定阅读顺序）

内部依赖图共 76 个模块、309 条边。入度前五：`console`(41)、`style`(27)、`text`(26)、
`jupyter`(20)、`segment`(18)；出度前三：`console`(29)、`text`(15)、`table`(13)。

结论：先读 `cells` → `color` → `style` → `segment` → `text` → `console`，
再按需读组件层。这也是本次标注采用的顺序。

## 6. 关键模块的边界如何确定

`console.py` 单文件 2688 行，未达 3000 行；但渲染管线是一个语义完整的整体：

```
cells/color/style/theme  ──►  segment  ──►  console  ──►  _win32_console
        (样式与度量)          (中间表示)     (渲染出口)      (平台后端)
                 text.py 提供带样式的字符串与排版原语
```

把上述 7 个文件（外加 5 个极小的辅助文件）视为一个模块，合计 8364 行，
既满足“关键模块不少于 3000 行”，又不会像“整个仓库”那样失去边界。
